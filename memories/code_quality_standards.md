後からリファクタリングで直すことになる設計上の問題は、最初の実装時点で正しく行うこと。

**Why:** ユーザーからの指示。リファクタリングは本来不要な手戻り作業であり、最初から適切な設計をすべき。

**How to apply:**
- 重複コードは発生時点でUtility/Helperクラスに抽出する
- GCHandle+BufferDataなどのボイラープレートは初回から共通メソッドにする
- .Last()等の危険なAPI使用は初回から安全な代替を使う
- ビルド警告は発生時点で即座に修正する（deprecated API、analyzer警告）
- 大きいクラス（300行超）は最初から責任分割して設計する
- 毎フレーム実行されるコードでのメモリ確保（List, string interpolation, ToArray）は最初から回避する
- マジックナンバーは最初から定数として定義する
- 例外処理は最初からログ付きで実装する（bare catch禁止）
- テストも機能実装と同時に書く（後付けではなく）

## アーキテクチャ原則（常に意識する）
- **単一責任原則**: 1クラス1責任。Viewにビジネスロジックを書かない。Rendererにモデル操作を書かない
- **依存の方向**: Models ← ViewModels ← Views。逆方向の依存を作らない
- **状態管理の一元化**: SceneModelが唯一の真実の情報源。UI側はバインディングで反映
- **レイヤー分離**: Rendering層はModelsを参照するがViewModelsを参照しない
- **イベント駆動**: 状態変化はイベント（PropertyChanged, SelectionChanged等）で通知。ポーリングしない
- **新規クラス作成時の設計判断**: 「このクラスは何の責任を持つか」「既存のどのレイヤーに属するか」「既存クラスとの依存関係は適切か」を先に考える
- **機能追加時**: 既存の共通基盤（MathUtility, GlBufferHelper等）を先に確認し、再利用できるものは再利用する。新しいパターンが必要なら共通化を先に行う
- **プロジェクトの清潔さ**: 不要ファイル・未使用コード・古いコメント・デバッグ残骸を常に除去する。gitignoreを適切に維持。bin/obj/publish/test-resultsは都度クリーン。コミット前に不要ファイルが含まれていないか確認する
