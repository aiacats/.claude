# Windows アプリの GUI 検証

**コードを読んで「直ったはず」で報告しない。** 画面を操作して、自分で画像を見て確かめるまでが修正。

道具は 2 つ。`win-gui` MCP（find_window / click / type_text / key_press / capture_window /
screenshot / scroll）と、このスキルの `scripts/gui.ps1`（MCP では届かないところ）。

```bash
G=~/.claude/skills/windows-gui-testing/scripts/gui.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File "$G" <command> <args>
```

| コマンド | 用途 |
|---|---|
| `windows <プロセス名>` | そのプロセスの窓（Id / タイトル / ハンドル）を出す |
| `focus <ハンドル>` | **確実に**前面へ出す（`AttachThreadInput` 併用。ただの SetForegroundWindow は無視される） |
| `pin <ハンドル> [x y w h]` | 最前面に固定して位置と大きさを決める |
| `unpin <ハンドル>` | 固定を外す |
| `modclick <x> <y> [ctrl\|shift\|ctrl+shift]` | 修飾キーを押しながらクリック |
| `shot <x> <y> <w> <h> <out.png>` | 画面の一部を PNG で保存（ユーザーへ送る用） |

## 手順の型

1. **アプリを起動し、窓を特定する**。`gui.ps1 windows <名前>` で**ハンドル**を取る。
   以後はタイトルではなくハンドルで指す。
2. **`pin` で位置と大きさを固定する**（例: `pin <h> 40 40 1456 939`）。
   これをやると座標の換算が毎回同じになり、他の窓にクリックを吸われない。
3. **`focus` してから入力する**。キー入力は前面のウィンドウにしか届かない。
   PowerShell や別ツールを挟むたびにフォーカスは奪われるので、**入力の直前に毎回**呼ぶ。
4. 操作する。クリックは win-gui、修飾キー付きは `modclick`。
5. **キャプチャして自分で見る**。`capture_window`（PrintWindow なので隠れていても撮れる）で確認し、
   ユーザーへ送るものは `shot` で PNG に保存して `SendUserFile`。
6. 終わったら `unpin` して、起動したアプリとシミュレータを片付ける。

## 座標の換算（毎回ここで間違える）

`capture_window` は `max_width`（既定 1280）に縮小して返す。**画像の座標はそのままでは使えない。**

```
倍率 = 実際のウィンドウ幅 / キャプチャ画像の幅     # 例: 1456 / 900 = 1.6178
画面座標 = ウィンドウの左上 + 画像座標 × 倍率
```

`screenshot` に `region="x,y,w,h"` を渡すと**等倍**で返るので、こちらは足し算だけで済む。
細かい位置を測るときは region を使う。

## 踏んだところ（先に読む）

- **同じ名前の窓が複数ある**。`find_window` は部分一致なので、端末のタイトルが
  `◐ ftpDeck` だと、アプリではなく端末を掴む。**プロセス名からハンドルを取る**こと。
- **フォーカスを奪われてクリックが吸われる**。別のアプリが前面にあると、その座標のクリックは
  そちらへ行く。症状は「押したのに何も起きない」。`pin` + `focus` で防ぐ。
- **`SetForegroundWindow` 単体は効かない**。Windows が無視する条件がある。
  `gui.ps1 focus` は `AttachThreadInput` で結び付けてから呼ぶ。
    - ただし**前面のアプリが固まっていると `focus` ごと返ってこない**。入力キューを繋いだ相手が
      メッセージを回さないためで、症状は「コマンドが 120 秒で打ち切られる」。
      `IsHungAppWindow` で見て、固まっていれば結び付けずに呼ぶようにしてある（2026-09-23）。
- **アプリがマウス入力だけ受け付けなくなることがある**（キーは通り、窓は応答する）。
  ウィンドウを掴み損ねてスナップ操作を繰り返した後に WebView2 で踏んだ。
  **起動し直すと直る**。入力が効かないときは、まず他のアプリ（タスクバー等）を押して
  注入そのものが生きているか確かめてから、アプリを疑う。
- **長い文字列の `type_text` は落ちることがある**。120 文字のパスを打たせたら 1 文字しか
  入らなかった。長い入力は避ける設計にする（プリセットを用意する、リモート側の root を
  変える、短いパスで試す）。入れるなら分割して、**入った内容をキャプチャで確かめる**。
- **数値入力欄はトリプルクリックで全選択できない**。`Ctrl+A` を使う。
- **`click_text` は日本語 OCR が効かない**。座標でクリックする。
- **PowerShell スクリプトに日本語を書くなら UTF-8 BOM 付きで保存する**。
  Windows PowerShell 5.1 は BOM 無しを ANSI として読み、コメントが壊れて構文エラーになる。
- **ダイアログは別ウィンドウ**。確認・エラー・入力の窓はアプリ本体と別のハンドルを持つ。
  「押したのに進まない」ときは `windows` で窓が増えていないか見る。

## 見るときのチェックリスト

キャプチャを「問題なさそう」で済ませず、下の項目を順に点検して結果を報告する（Web・Unity の UI でも同じ）。

運用:
- **絶対評価より相対評価**。基準（デザインモック・正常時のスクショ・同じアプリの他画面）と並べて差分を問う。
  基準が無いときは「基準なしの絶対評価」だと報告に書く。
- 1〜2px のズレは全体像では分からないので、**怪しい所は region で部分拡大**する。
- 目視は一次フィルタ。「問題なし」の判定は見落としうるので、機械的な判定（`find_text` / `wait_for_text` /
  `get_pixel_color`、Before/After の画像 diff）を最終ラインにする。
- 動きの違和感（easing・応答の遅れ・ホバー）は静止画では判定できない。下の「録画する」へ。

点検項目:
1. **整列** — 揃うべき要素の左端・中心線のズレ、グリッドから外れた要素
2. **余白** — マージン・パディングの不整合、詰まりすぎ・空きすぎ、非対称
3. **視覚階層** — サイズ・太さ・色で「最初に見るべき場所」が作れているか。全要素が同じ強さになっていないか
4. **近接** — 関連要素がまとまり、無関係な要素が離れているか
5. **タイポグラフィ** — フォント・サイズ・ウェイトの種類が多すぎないか、行間が窮屈でないか
6. **コントラスト** — 文字と背景の判読性、有効/無効・選択/非選択の区別
7. **未スタイル** — 既定のままのボタン・システム標準色の混入（スタイルシート未リンクの兆候）
8. **クリッピング / オーバーフロー** — 文字切れ、はみ出し、重なり
9. **プラットフォーム慣習** — OK/キャンセルの並び順、閉じるボタンの位置
10. **ユーザーの好み** — `~/.claude/rules/taste/general.md` の「見た目」（ダーク基調・絵文字なし・太字控えめ・値の変化でレイアウトが動かない 等）

## レイアウトが崩れたときの調査順序

1. **スタイル未適用を最初に疑う** — スタイルシートのリンク（UXML↔USS、ResourceDictionary 等の参照）→ セレクタ優先度・継承 → 計算済みスタイル。
2. **サイズ** — アンカー・ピボット・flex 設定、min/max サイズ、親コンテナの制約。
3. **環境** — ウィンドウリサイズ、解像度・アスペクト比、DPI（4K では `SetProcessDPIAware` が要る）。
4. **コンテンツ** — 長文・日本語文字列のオーバーフロー、空データ。
5. **状態網羅** — 初期・ローディング・エラー・空・大量データの各状態でキャプチャする。

## 動きが論点なら録画する

止め絵で伝わらないもの（操作の流れ・アニメーション・応答の遅れ）は `screen-recording` skill。
