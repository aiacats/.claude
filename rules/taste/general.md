# ユーザーの好み・こだわり（全プロジェクト共通）

過去に何度も直させた箇所から起こした、このユーザーの判断基準。**最初からこの形で作る**。
罠（こうすると壊れる）は `rules/traps/`、方針は `CLAUDE.md`。ここは「こちらの方が好き」の置き場。

- 既定であって絶対ではない。案件側の指示（プロジェクト CLAUDE.md・その場の依頼）が優先する。
- 新しく「直させられた」ら、2 回目の時点でここへ足す（1 回きりはプロジェクトメモリ）。

## 見た目

- **ダーク / モノトーン基調の、エンジニアツール風（コンソール調）で無骨かつモダン**にする。
  原色ベース・緑ベース・既定の背景（Skybox のまま等）にしない。
- **絵文字を使わない**。ラベル・ボタン・ガイド文・README の見出しも同じ。アイコンはアイコンライブラリ（React なら lucide-react）。
- ダーク背景に**黒や暗すぎる文字を置かない**。ライトグレー以上にする（明るいボタンの上の文字は黒でよい）。
- **太字を多用しない**。強調は本当に要る 1 箇所だけ（VR 空間の小さい文字は例外で太字・白）。
- 区切り線・強調色は「控えめだが判別できる」中間の強さ。
- **状態は色で意味を持たせる**: 赤 = 未着手・要対応 / 青か黄 = 進行中 / 緑 = 完了・確定 / 灰 = NG・無効。
  小さなドットより**背景のハイライト**で示し、色は彩度高めにする。選択ハイライトと紛らわしい色（黄など）は他の意味に使わない。
- **整列にこだわる**。ラベルとコントロールの中心線、頭、左端を揃える。名前の列は左寄せ。
- **値の変化・再生開始・保存でレイアウトを動かさない**。数値欄やファイル名欄は固定幅、パネルは固定サイズ、保存でスクロール位置を戻さない。
- **要らない要素は置かない**。役目を終えたボタン・欄・タブ・装飾は、聞かれる前に消す提案をする。
- 同じ情報・同じ見出しを二重に出さない（ヘッダにあるならセル側は値だけ、同じ総称が続くなら 2 行目以降は空欄）。
- 既定のままのコントロールを置かない（青い長丸のスライダーつまみ、素の text input、文字だけの「更新」ボタン）。
  スライダーのつまみは普通の丸、再読み込みはアイコン。
- 項目が多い一覧はフラットに並べず、分類で階層化する（部署 > ロール > メンバー）。
- 選択肢を横にずらっと並べない。普通のプルダウンか、埋もれるならオーバーレイで出す。
- 切り替えはパッと変えず**フェードを挟む**（色の切り替え・ボタンの消え方・暗転）。
- **3D モデルはポリゴンを惜しまない**。円筒の角が見える分割数、面取りの無い箱、平らな面のままの陰影は「粗い」と言われる
  （2026-10-07 にプロップ・幕・会場全体で 3 回）。輪郭が滑らかに見える分割数と、角の面取り・滑らかな陰影を最初から入れる。
- **3D の機材・小物は、そのアセット単体でも成立する作り込みにする**（2026-10-08 ユーザー: 「カメラのディティール荒過ぎる。
  しっかりそのアセット単体でも成立するぐらいにモデリングして。これは他のオブジェクトにも言える話」）。会場の中で遠目に
  それっぽく見えるかではなく、取り出して寄って回して見ても実物に見えるか（製品の写真と並べて見比べられるか）で判断する。
  作る前に製品の写真と寸法を集め、作った後に単体で 4 方向から撮って写真と見比べる。
  ただし**製品の丸写しはしない**（2026-10-08 ユーザー: 「丸パクリはしないように」）。資料から取るのは寸法・比率・部品の構成と
  付き方だけで、外装の造形は自前で起こす。メーカーのロゴ・製品名は入れない（文字は現場で意味のあるもの、カメラ番号などだけ）。
  作り込みの度合いは用途に合わせる（ライブ会場なら、現場で実際に使う構成と付属品まで。2026-10-08 「あくまで用途はライブ用」）。

## 文言

- **画面の文字は英語**。コメント・ログ・コミット・README・報告は日本語。
  既存の日本語 UI を一括で英訳しには行かない。今回触る画面から揃える。
  （エンドユーザー向けの日本語コンテンツは例外。案件の指示に従う）
- **名前は端的な名詞**。「書き出し開始」で足りるなら「Timeline を書き出す（時間がかかります）」とは書かない。
  短い一般名詞・略称を好む（Human → Actor、MotionCapture → MoCap）。
- **説明文を常時表示しない**。使い方・前提・注意・値の決め方は、ラベル横の i / ? アイコンかツールチップへ入れる。
  常に出してよいのは、今この瞬間の判断に要るもの（エラー・警告・進捗・件数）だけ。説明が常に見えていると、本当に見るべき警告が埋もれる。
  Unity の Editor ウィンドウなら、HelpBox を並べず `GUIContent(label, tooltip)` か折りたたみにする。
- **用語は現場・業界の正式な呼び方**に揃える（Line ではなく Universe、Zoom ではなく FocalLength）。迷ったら聞く。
- 日本語で並列に書くときは読点ではなく中黒「・」で区切る。
- 単位は現場の感覚に合わせる（機材寸法は mm、画面サイズは 縦×横）。

## 名前の付け方

- **複製の連番は `_1` `_2`**。`Copy` や ` (1)` を付けない。新規作成の既定名は「種類名_作成順番号」。
- 出力ファイル名は、由来が分かる名前にして自動で連番を振る（Unity Recorder 風）。書き出す前にファイル名をプレビューで見せる。
- 所有者名・パッケージ名は `aiacats`（UPM は `com.aiacats.*`、Tauri の identifier は `jp.aiacats.*`）。

## 操作感

- **操作体系は Unity / Blender / After Effects / Explorer に揃える**。パネルは移動・ドッキング・幅変更ができるようにし、
  パネル左上から種類を切り替えられるようにする。迷ったら「Unity ならどう動くか」に合わせる。
- **数値欄は入力欄 + ラベルの左右ドラッグで増減**（Unity の Inspector と同じ）。スライダーにするのは見た目の調整値だけ。
- **並べ替えはドラッグ & ドロップ**。上下ボタンや「表示順」の数値欄は作らない。
- **複数選択と一括編集を最初から効かせる**。Ctrl で追加、Shift で範囲、ボックス選択。複数選択中に値を変えたら全部に適用する。
- キー操作の慣習: Enter = 確定（セルを抜ける）、Shift+Enter = 改行、Esc = 閉じる、Ctrl+C = コピー。
  Enter を押しただけで項目が追加されるような、意図せず確定してしまう動作は作らない。
- **取り返しのつかない操作の前に確認を挟む**（終了・削除）。誤って押しやすいキー（Esc で終了など）は二度押しで判定する。
- 本番中に使うアプリは、キーボードショートカットをまとめて無効にできる口を持たせ、頻繁に押す操作は修飾キーなしの単キーにする。
- **編集は明示保存**。入力途中に自動保存して邪魔をしない。必須項目が空のまま保存しようとしたら警告する。
- **状態を覚える**。保存時の画面を完全に復元し、タブ・フィルタ・ピン留め・折りたたみも保持する。
- 起動時の状態は表示どおりにする（チェックが外れているなら Off）。設定セクションは開いた状態で始める。
- ファイル・フォルダの指定はエクスプローラーで選べるようにする。書き出しの既定の保存先はアプリの隣。
- 選べる値（デバイス・FPS・接続先の部屋）は手入力させずドロップダウンにする。検出できるものは検出して並べる。
- FPS などの計測表示は、アプリ全体の右上に置く（シーンビューの右上ではない）。
- 機能の有効化や記録の開始は、ユーザーが明示的に行う。勝手に始めない（受信の On/Off も置く）。

## 作り方

- **何か作るときは、資料を集めてから進める**（2026-10-08 ユーザー: 「何か作るときは資料集めてから進めてね」。
  LED の施工・カメラ機材と 2 回、手元の知識の目安で組み始めて直された）。実在の物は、メーカーの仕様書・取扱説明書・製品情報で
  寸法と作り（何に支えられ、何に付くか）を確かめ、出典をコードのコメントと報告に書いてから形を作る。見つからない値は「目安」と明記する。
  資料集めは 1 区分 10 分まで（2026-10-08 ユーザー指定）。足りなければ集まった分で進め、足りない所を別途報告する。
- **仕組みはシンプルに**。凝った仕組みを提案する前に、素直な方法で済まないかを先に考える。
- **参照は手で指定させず、自動で見つける**。シリアライズ欄を増やさない（自分の GameObject から探す、Timeline 上のトラックから拾う）。
- **一度合意した計算方法・挙動・レイアウトを黙って変えない**。別の箇所を直したせいで、以前良かった実装が消えることが最も嫌われる。
  直す前に「今うまく動いているもの」を列挙し、直した後にそれが残っているかを確かめる。
- 元データ・元の実装は、失わない形で足す（元の色は必ず戻せるようにする、将来使う実装は消さずに共存させる）。
- 新しく書くものは、最初から共通化・Utility 化する（後でリファクタリングして直すくらいなら最初からやる）。プロジェクトを常に清潔に保つ。
  既にある、分裂した実装をまとめるかどうかはユーザーに返す。
- 実データが無いときに、映像・値・状態を「それっぽく」出さない。無いなら無いと、理由付きで画面に出す（「Not ready」「Stopped」「(not found)」）。
  保存していた値がその端末に無くても、別の値へ黙って付け替えない。
- アプリの役割を広げない（見るアプリに操作機能を足さない、ランチャーにチャット UI を足さない）。
  新しい常駐ツールは別アプリにせず、既存の常駐（SessionControl）のタブとして足す。
- 対になる機能は両側を揃えて作る（Sender と Receiver、Export と Import）。片方にだけ足さない。
- 内部表現は正確に、編集 UI は人に分かる形にする（回転は内部を Quaternion、表示を Euler、Inspector はローカル基準）。
- **今の値はログに流さず、画面（Inspector）に出す**。受信中の値・検出中のオブジェクトはプレビューで見せ、デバッグログは切り替えられるようにする。
- 新しいアプリは既存の自作プロジェクトのスタックに揃える（Tauri 系は Shifter / Sequence が手本）。
  配布物は 1 つの exe で完結させる（バックエンドと GUI を 1 アプリで起動）。
- Unity では Unity 標準の仕組みに乗せる（ポストエフェクトは Volume、UI は UI Toolkit、シェーダーは URP/Lit を下敷きに）。
- 外部依存は latest を追いかけず、バージョンを固定する（URL と SHA を固定し、リリースごとに更新する）。
- 軽さを優先する。GPU で済む処理は GPU で行い、描画側の FPS を測れるようにしておく。

## 進め方・報告

- **書き出し（FBX など、外へ渡す成果物の生成）は、ユーザーが「書き出して」と言ったときだけ行う**（2026-10-07 ユーザー指示）。
  作業の区切りごとに自分から書き出さない。点検・コミット・報告はいつもどおり行い、報告では「書き出しは未実施」と添える。

- 破壊的な操作以外は確認なしで進める。**順番は任せてもらっているので、止まらず行けるところまで進める**。
  （新しい実装の手法は最初に提案して承諾を得る。承諾を得たあとは、途中で止まらず最後まで進める）
- **作業中に届いた追加の要望は積んでおき、今の作業を終えてから順に取りかかる**。
  今の作業の方針そのものを変える軌道修正だけは、その場で反映する。
- 検証（UI テスト・ビルド・エラー修正）は自分の責任で最後までやる。「動かして確かめて」と言わせない。
- 判断を仰ぐときは**選択肢で出す**（AskUserQuestion）。推奨を先頭に置く。
- 要望と技術的な制約・排他関係がぶつかったら、黙って片方を落とさず、理由を説明したうえで選択肢で選ばせる。
- **一度決めた前提**（構成・既定値・対象・配布方式）はプロジェクトメモリに残し、聞き直さない。変えたいときは、選んだ理由を崩さないかを添えて提案する。
- **手を入れるのは依頼の文言が指す範囲だけ**。脇に置くと言われた機能・対象外の画面には触らない。似た箇所へ広げるかはユーザーに返す。
- 本番ライブ機・本番アセット・信号経路（OSC / DMX / LiveLink）には不可逆な変更をしない。試すのは複製で行い、経路を変えるのは確認を取ってから。
- その場限りの特例として足したものを理由に、プロジェクト CLAUDE.md や方針文書を書き換えない。前例としても扱わない。
- ブラウザ操作で他人の Drive 等からファイルを取るときは、黙って始めず、理由を添えて先に聞く。
- push の前に、同じ作業の細かいコミットを 1〜3 個へまとめ直す（まとめる前にバックアップのタグを打つ）。手順は `commit-squash` skill。
  まとめ直しても、コード / README / ドキュメント / claudeLog を分ける粒度は保つ。
- git worktree は作らず、共有のチェックアウトで直接作業する（node_modules / target が worktree ごとに増えてディスクが足りなくなる）。作ってしまったらすぐ消す。
- **作業のあとの報告は、直前に罫線（`---`）を 1 本引いてから書く**。途中経過の文章と報告の境目がひと目で分かるようにするため
  （ユーザーは報告を追うとき、どこから読めばよいか迷っていた）。罫線は報告の開始位置に 1 本だけ引き、報告の中の区切りには使わない。
- 「可否だけ」と聞かれたら可否だけ答える。聞かれていない説明を足さない。
- 数値や結論には根拠を添える（「何を根拠に 6 秒？」と聞かれない形で書く）。
- 一段落したら、「足すとよさそうな機能」「直すべき実装」を 3 件以内で添える（このユーザーは毎回それを聞いてくる）。
- 本番へのデプロイの時期はユーザーが決める案件がある。プロジェクトメモリに許可が無ければ、デプロイ前に聞く。
